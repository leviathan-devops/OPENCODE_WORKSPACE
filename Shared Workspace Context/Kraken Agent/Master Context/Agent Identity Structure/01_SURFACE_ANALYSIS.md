# Surface Analysis — Agent Identity Structure

## Problem Statement

**The Problem:**
AI agents in multi-agent orchestration frameworks lack persistent self-awareness. When a session starts, the agent knows nothing about WHO IT IS beyond what fits in the system prompt. This causes behavioral derailment — an orchestrator acts as a solo builder, a reviewer doesn't know to review, etc.

**Symptom:**
During Kraken v1.2 build, the primary agent had access to `spawn_shark_agent`, `run_parallel_tasks`, and 5+ other Kraken-specific tools but used them ZERO times across 2 hours. It defaulted to vanilla sequential build behavior.

**Root Cause:**
No identity reinforcement mechanism. The agent had the TOOLS but not the IDENTITY to know WHEN and WHY to use them.

---

## First Principles

**Principle 1: Identity Precedes Behavior**
An agent cannot exhibit role-appropriate behavior without first internalizing role identity. Tools alone are insufficient — the agent must know it IS an orchestrator, not just HAS orchestrator tools.

**Principle 2: Context Decay Requires Reinforcement**
System prompts degrade over long sessions. Identity injection must be persistent or repeated to maintain behavioral consistency.

**Principle 3: Orchestrators Must Delegate**
By definition, an orchestrator's value comes from coordinating others, not from doing work directly. An orchestrator that doesn't delegate has failed at its core purpose.

**Principle 4: Identity Must Be Loadable, Not Generated**
Identity should be loaded from files (SOUL.md, IDENTITY.md) rather than generated by the agent itself. Generated identity is subject to the same hallucination risks as generated code.

---

## Scope

### In Scope
- Identity file structure per agent role
- Identity injection mechanisms (hooks, events)
- Identity content requirements (what each file must contain)
- Testing methodology for identity verification
- Integration with OpenCode plugin architecture

### Out of Scope
- Changes to underlying LLM behavior
- Model routing logic (handled by separate system)
- Agent-to-agent communication protocols
- Persistence layer (database) — identity is session-scoped

---

## Constraints

**Constraint 1:** Identity files must be readable before session begins (pre-load, not runtime generation)
**Constraint 2:** Identity injection must not break existing plugin hooks
**Constraint 3:** Identity must survive session compaction/recovery
**Constraint 4:** Fallback to vanilla behavior if identity fails to load

---

## Success Criteria

1. An agent designated as "orchestrator" delegates >80% of file-writing tasks to sub-agents
2. An agent with identity files shows measurable difference in tool usage vs. same agent without
3. Identity injection adds <500ms to session startup
4. Identity is recoverable after compaction via persistence mechanism

---

## Open Questions

1. **Q:** Should identity be loaded once at session start, or reinforced periodically?
   **A:** Likely both — load at start, reinforce on each new task assignment

2. **Q:** How to handle identity for agents spawned mid-session?
   **A:** Identity should be passed to sub-agents via context injection

3. **Q:** What's the minimum viable identity (1 file vs 4 files)?
   **A:** SOUL.md alone provides significant improvement; full benefit requires all 4

4. **Q:** How to prevent identity drift during long sessions?
   **A:** Periodic "identity check" prompt or hook that re-injects identity summary
